An update on the Sashiko patch-review system

By Jonathan Corbet
October 5, 2026
Kernel Recipes
Patch review has long been one of the limiting constraints for the kernel project (and most others); there just aren't enough people to properly review all of the code that is submitted for inclusion. The Sashiko system, which uses a large language model (LLM) to generate reviews automatically, offers the prospect of some relief, and has already become an important part of the kernel's development process. At the 2026 edition of Kernel Recipes, Roman Gushchin, the maintainer of Sashiko, provided an overview of how the system works and what is being done to improve it.

The primary goal driving the development of Sashiko, he said, is preventing new bugs from entering the kernel. All of the code (excepting the LLM, of course) is open source and has been donated to the Linux Foundation. The main Sashiko instance runs on Google's Gemini LLM, but the code works with a number of popular models. It watches kernel mailing lists, and reviews all of the patches that it sees there. Those reviews show up in the central sashiko.dev site, which is sponsored by Google.

There are a number of reasons to create a dedicated review harness for the kernel, he said. Initially, this project started with a generic LLM, but the quality of the reviews was not high enough. LLMs are highly dependent on the context they are given. They need enough information, but not more; providing too much information will lead to "strange effects". Security is also a significant concern; maintainers rely on Sashiko to judge code, and have to be confident that it has not been subverted. That means, among other things, a fair amount of effort to protect the system against prompt injection. Efficiency is also a concern for a system that must be able to review 1,500 or more patches every day.

The design principles behind Sashiko include "full transparency"; everything is available. That includes the code, prompts, thought chains, and generated reviews. Development is guided by benchmarks that measure both the ability to detect problems and false positives. All aspects of Sashiko are opt-in, he said, with developers able to control the sending of email. The project aims for a "kernel-like development culture".

Sashiko is structured as a multi-stage pipeline; there are 11 stages now, with another one to be added soon. The first seven stages each review a patch from a different angle; one specializes in locking, another in resource control, one in security, and so on. Each stage produces "concerns" that are passed to the later stages, the eighth of which performs deduplication. Stage nine handles conflict resolution, stage ten performs validation and severity calibration, and the final stage generates the reports. It is important, he said, to separate discovery from verification. If the system is asked to only report bugs that it can absolutely prove to exist, it will miss a lot of problems; enumerating concerns then trying to falsify them afterward works better.

In its first six months, Sashiko has generated over 170,000 reviews across 91 mailing lists. That work has required over 18 million Git invocations to look up information. The early versions were slow; it turns out they were I/O bound due to all the checking of Git repositories. It took 15 hours to review a patch; now a review takes 15 to 30 minutes.

The benchmark works by taking 1,000 known regressions with known fixes; each patch that introduced a regression is re-reviewed without the fix, and an LLM scores the result. Currently Sashiko finds just over half of those bugs, all of which originally got past human review.

Evaluating the impact of Sashiko in the kernel community is difficult, he said; the system is still too new. It is also hard to measure; a lot of the bugs it finds are quietly fixed in subsequent patch postings. There are, he said, 1,215 commits in the kernel repository citing Sashiko, and its reviews have seen 6,600 email replies from 1,015 kernel developers. From this, he concludes that the system does, indeed, work. But whether it results in improved kernel code is harder to measure. He has spent some time looking at kernel commits fixing a patch that had been applied within the previous 60 days; it looks like there was less of that happening for 7.1, but it is too early to say for sure. But patches that were reported as "clean" by Sashiko had few fixes, while those with reported problems required more fixes.

A relatively new Sashiko feature is a local, terminal-based review mode. It can be installed with: 

    $ cargo install sashiko

After that, it's just a matter of configuring one's LLM key and running it in the terminal.

When Sashiko reviews a patch, it also tends to find existing bugs in the surrounding code. Developers have not always welcomed hearing about those bugs; fixing them is not part of what they set out to do. So now Sashiko is suppressing those reports and putting them into a separate database. There are about 5,000 bugs in that database now; anybody who is named in the MAINTAINERS file can query it to see the bugs that have been reported in their subsystems. One problem is that nobody has time to maintain this database and, for example, clear out entries for bugs that have been fixed; he is hoping to set up some agents to do that work.

Also new is "Sashiko for Sashiko", which reviews changes to Sashiko itself. Meanwhile, there is, evidently, somebody out there running a Sashiko instance to review OpenBSD patches; he does not know who that is, but would like to learn from their experience. In the future, Sashiko instances may be set up for projects like Git, LLVM, or QEMU. While many of the prompts used by Sashiko are kernel-specific, much of what is there is more general. He has also seen developers who are using Sashiko in their own workflow; Sashiko was meant for maintainers, but its use by developers is expanding as well.

There are, of course, always ways in which the tool can be improved. For example, reviews for large changes are notably worse than those for small ones. Developers can be frustrated by its tendency to keep finding new bugs in code it has reviewed before, even if the code itself has not changed. It still does not find all of the bugs, and it still makes up bugs that do not exist.

Gushchin concluded by saying that the Sashiko project could use more help; new contributors are welcome. Providing feedback on its reviews is perhaps the most important and helpful way to contribute. The development of subsystem-specific prompts is always welcome. Finally, there is always value in adapting Sashiko for other projects that might benefit from automated patch review.

A member of the audience (not me, surprisingly) remarked that many of the prompts appear to duplicate information that is in the kernel's documentation, and that some of the other information there would be useful to human developers as well. Perhaps, he suggested, the prompts should be a part of the kernel's documentation. Gushchin agreed in principle, but said that the situation is complicated. Sashiko is meant to work with older kernels as well as the current mainline, he said, and the prompts tend to change more quickly than the kernel's release cycle. Both of those points argue for keeping the prompts, or at least a subset of them, outside of the kernel.

Mark Brown remarked that, when Sashiko needs information from outside of the kernel tree, the result is often "hot garbage"; he wondered if that situation could be improved. Architecture-specific code tends to be one area where this behavior is seen. Gushchin suggested that giving the model access to data sheets might help, though that may not always be legally possible.
